# Mobile Google Flow media workspace (iPhone)

The dashboard is the one place where you: add verified product photos, copy each scene's Gemini prompt, open Google Flow, upload the clips you made, approve or reject each clip, and then (only when **every** clip is approved) get the render job for the Mac. **Google Flow stays manual**: no Flow automation, no Veo API, no automatic paid generation. Media rights stay a manual check: owning the product does not clear anyone else's images or video.

## Workflow

```
SCRIPT_APPROVED
 ├─ ① product photos (≤ 4)     dashboard 📱 card → saved in Drive, linked into PRODUCTS
 ├─ ② Gemini production plan    scene prompts from the approved narration + your photos   (existing, PR #11)
 ├─ ③ per clip (S1 … Sn):  [프롬프트 복사] → [Google Flow 열기] → make the clip in Flow by hand
 ├─ ④ upload the clip from iPhone Safari → preview → 승인 / 반려·다시 만들기 (or 교체 업로드)
 ├─ ⑤ all clips APPROVED → 렌더 작업 파일 → Mac:  fetch-clips → render   (Mac re-checks IDs + checksums)
 └─ ⑥ final video approval (③ checkpoint) → Instagram + ManyChat by hand (④ checkpoint)
```

## What is built

| Part | Behaviour |
|---|---|
| **Reference photos** | Browser shrinks the photo (≤ 2048 px JPEG), Apps Script checks the real file type from its bytes (PNG/JPEG/WebP), ≤ 3 MB, ≤ 4 per product, no duplicates (MD5). Saved to `Reels Factory / <상품ID> / references` (private) and the link is **appended** to that product's `검증된 제품 이미지` cell: other cells, other rows and existing notes are never changed. Needs a rights confirmation tick; the product row is re-read before writing. If the PRODUCTS column does not exist nothing is created (you add the header yourself). |
| **Clip upload** | Chunked, resumable (see below). Target clip comes from the reel's own clip list (`S1`…), the Drive file name is generated by the server; type (`mp4/mov/m4v`), size (10 KB – 100 MB) and a rights confirmation are validated first. Files land in `Reels Factory / <상품ID> / <릴스ID> / versions`, private. |
| **Versions** | Every upload is a new version (`v1`, `v2` …). A replacement marks the previous version `SUPERSEDED` (its approval is void). Rejected, superseded and approved versions all keep their Drive file IDs; nothing is deleted. A file with the same Drive checksum as any version of the reel is refused (an upload we just made is moved to the trash; a file you put there yourself is left alone). |
| **Review** | 승인 / 반려 on the current version only (a rejection needs a reason). Approval re-checks that the Drive file is still the uploaded bytes. Approvals belong to one approval of the script: withdrawing the approval or changing the script voids them. Every upload/approve/reject is in AUDIT (`CLIP_UPLOADED/APPROVED/REJECTED`). |
| **Render gate (server)** | For reels with a Gemini production plan, the job file is issued only when every clip is APPROVED, and each approved file is re-checked in Drive (same bytes, not trashed). The job carries `clipManifest`: per clip the Drive file ID, MD5, size, version, approver. |
| **Render gate (Mac)** | Independent of the dashboard: a planned job without a complete manifest for this approval is refused; every clip the render would use must be in the manifest **and** have the approved MD5 (a swapped file, an older version, an unapproved per-cut override, or an extra clip such as `S3b` all stop the render **before any TTS**). `fetch-clips` downloads exactly the approved files by Drive file ID and refuses a download whose size/MD5 differ. |
| **Fallback** | If direct upload is slow or fails: upload with the Drive app into the reel's folder, press *Drive 동기화* (제작 계획 card), then *이 파일 연결* on that clip. Only files in that reel's folder, of the right type/size, with a Drive checksum can be attached. |

Reels **without** a production plan keep the earlier flow (local clips, no clip gate, no manifest). The gate applies to every reel that has a plan.

## Can a phone upload large videos? What I found (and what is not tested)

| Question | Finding |
|---|---|
| `google.script.run` payload | Community measurements put the cut-off at ~52 MB per call, i.e. ~37 MB of raw file after base64 ([tanaike, resumable upload for web apps](https://tanaikech.github.io/2018/05/17/resumable-upload-for-web-apps-using-google-apps-script/), [50 MB limits](https://tanaikech.github.io/2024/07/11/uploading-large-files-to-gemini-with-google-apps-script-overcoming-50-mb-limit/)). Not confirmed on an official Google page. Flow clips (8 s) are usually far smaller, but a single call is not a safe design. |
| Drive blobs | `DriveApp.createFile` is limited to ~50 MB; the whole file would also have to sit in Apps Script memory (6-minute run limit). |
| **Design chosen** | Browser sends 1.5 MiB chunks (6 × 256 KiB) with `google.script.run`; Apps Script forwards each to a **Drive resumable session it opened with the operator's own OAuth token** (`ScriptApp.getOAuthToken()`). Drive requires non-final chunks to be multiples of 256 KiB and answers `308` with a `Range` header telling where to resume ([Drive upload guide](https://developers.google.com/workspace/drive/api/guides/manage-uploads)). No file is ever held whole in Apps Script, and no Drive token is exposed to the browser (the session URL stays in the server-side user cache for 6 h). |
| Alternative rejected | Browser → Drive directly with an access token: faster, but hands a Drive token to page JavaScript. |
| iPhone Safari | A file picker with `accept="video/mp4,video/quicktime"` and `File.slice` + `FileReader` are standard Safari features; the page reads one chunk at a time, so memory use stays small. **Not tested on a real iPhone.** |
| Auth | The web app already requires the signed-in Google account and `RF_REVIEWERS`; every upload call re-checks it, and a chunk call is only accepted from the account that started the upload. |
| Retry / progress | Each chunk is retried; after a doubtful failure the server asks Drive where to resume (`apiClipUploadStatus`). Progress bar and MB counter in the page. |
| Limits | 100 MB per clip (`MEDIA.CLIP_MAX_BYTES`), `UrlFetchApp` 50 MB per request (chunks are 1.5 MB), 6-minute execution (each call handles one chunk). |

**Honest status: the whole path is tested against an in-memory Drive model that enforces the same protocol rules (256 KiB chunks, `Content-Range`, `308`/`Range`), not against real Google services.** Real-service checks are listed in the PR and must be done once before relying on it (below).

## Setup (once)

1. **Google Sheets:** **릴스 팩토리 → 시트 준비** → 예. Adds the REELS column `장면 클립(JSON)` (existing cells untouched). PRODUCTS needs the column `검증된 제품 이미지` (right of column I, added by you).
2. **Apps Script:** paste `dist/ReelsFactory.gs`; run **코드 버전 확인** (`2026-10-11 · flow-media-workspace 5`); deploy a **New version** of the web app. **No new OAuth scope** (the `drive` scope came with the production planner; `UrlFetchApp`/`CacheService` need no extra one). If you have not yet authorized the Drive permission, do it when prompted. Optional Script Property `RF_FLOW_URL` (https only) to change the "Google Flow 열기" link (default `https://flow.google`; `labs.google/fx` redirects there).
3. **Mac:** `git pull`; `gcloud auth login --enable-gdrive-access` once; `renderer/.env` as in [mac-install.md](mac-install.md).
4. **Daily (Mac):** `npm run render:fetch-clips -- --job renderer/jobs/<file>` → `npm run render -- --job … --dry-run` → render.

## Real-service checks to do once (not yet done)

1. Upload a 5–20 MB MP4 and a `.MOV` from iPhone Safari on Wi-Fi and on cellular; confirm it lands in `versions/`, is private, and the preview plays.
2. Turn Wi-Fi off mid-upload and retry: confirm the resume works (or note that it restarts).
3. Confirm Drive returns `md5Checksum` right after the upload and the duplicate check works.
4. Upload a reference photo straight from the iPhone camera roll (HEIC) and confirm Safari hands the page a JPEG it can shrink.
5. `fetch-clips` on the Mac with a real token; confirm the MD5 check passes and a tampered local clip is refused.
6. Check that the owner can open the Drive preview iframe inside the web app (third-party cookie settings in Safari can block it; *Drive에서 열기* is the fallback).

## Security notes

- The browser is not trusted: clip key, file type, size, rights confirmation, version and account are all checked again on the server; names and folders are generated server-side.
- Files stay private in your Drive (never shared); the OAuth token never leaves Apps Script except in requests to `googleapis.com`.
- The Drive scope is broad (`drive`) because the narrower `drive.file` cannot see files you upload yourself with the Drive app (needed for the fallback). The code reads images, creates folders and files, lists a reel's folder, and moves **its own rejected duplicate uploads** to the trash; it never edits or deletes anything else.
- No API secret reaches the browser; the affiliate URL is not in the job file.
